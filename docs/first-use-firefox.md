# First-use Firefox and required extension provisioning — browser prerequisite stage

## Included / not included
This patch implements the missing browser prerequisite for the current 1.4 client: first-use consent, app-owned Mozilla-signed Firefox runtime, AdBlocker Ultimate and SponsorBlock policy provisioning, progress and re-use of per-profile login data. It also reserves a separate no-media-extension browser purpose for future Square checkout. It DOES NOT implement Square authorization, customer-household mapping, invoices, payments or Projects. Account remains the current device-update panel until the billing backend/client stage is supplied. No fake account balances or payment success states are added.

## Deployment
The developer-side installer resolves the exact approved extension GUIDs from Mozilla Add-ons API using the fixed slugs adblocker-ultimate and sponsorblock. It refuses malformed/unavailable metadata rather than guessing IDs. Those IDs and official AMO install URLs are bundled as a small public manifest in assets/native. The client does not send customer data to AMO to resolve extensions.

Run the patch installer on the development PC with -Release to run tests then the existing single Windows build/sign/publish/paused-registration pipeline. It blocks changes during an unfinished or concurrent release, backs up source outside the project, checks existing source hashes and validates the native helper syntax. -RetryChecks reruns checks without overwriting installed source after a targeted repair. A new patch version of at least 1.4.1 is selected; the build number remains automatic. Backend and download mounts are not touched.

## First use on the target PC
Click a web app. If the owned browser/profile is not ready, choose Install and open (or Prepare and open). The app downloads only from Mozilla's official latest Windows x64 full-installer endpoint, requires a valid Mozilla Corporation Authenticode signature, and runs only the documented /ExtractDir mode. It does not run a general browser installation, set the default browser, install a maintenance service, change personal Firefox policies, create shortcuts or disable signature enforcement. Windows endpoint/security policies may still block executable extraction and must not be bypassed.

The complete signed Firefox application is moved into LOCALAPPDATA/MILLITOPTV/managed-browser/media/current. The new runtime uses the EXISTING LOCALAPPDATA/MILLITOPTV/firefox/profile-<household-profile-id> directory. Existing Millitop Firefox cookies/logins are not deleted, imported, exported or copied into another family member's profile. Personal Firefox profiles are not read. Firefox's normal saved-login/session behavior applies; site expiry and MFA still require reauthentication.

The runtime's distribution/policies.json force-installs the exact two approved signed extensions through official AMO URLs. Signing checks are not weakened. A first-time/changed-version/changed-policy warm-up opens only about:blank in an owned session; the requested site is not loaded until the two required add-ons are confirmed active. Setup then requests normal closure of ONLY the owned warm-up windows. It does not forcibly terminate personal Firefox. Unknown/blocked readiness stops with an error and instructions, not an unprotected site launch. Existing organization policies are respected; conflicting policies can block preparation.

Readiness inspection uses Firefox's app-owned extensions.json add-on-registration data. This is not a public stable add-on-management API; future Firefox format changes can cause a fail-closed setup error. The exact installed version and both extension behaviors require a real Windows pilot. The five-second startup grace and cached version/policy marker are readiness signals, not a guarantee every content script has executed on every possible site. Ad blocking and SponsorBlock do not guarantee every advertisement is removed; SponsorBlock primarily skips known crowdsourced YouTube segments.

## Payment isolation foundation
FirefoxBrowser.open adds payment:true for trusted future billing code. It selects a separate managed-browser/payments/current runtime and payments-profile-<id> data directory, with media add-ons blocked by policy. Policies are installation-scoped, so a separate purpose needs a separate runtime directory. This purpose is NOT automatically applied to arbitrary local URL tiles. No current payment action or Square link is claimed by this stage. The future billing backend must verify customer ownership and return a fresh trusted Square URL before invoking it.

## Failure/recovery
Setup progress is modal; the user can decline before starting. After extraction begins the app requests that it remain open. Downloads are size/time bounded, verified before execution, and use a private per-user directory. Extraction and extension warm-up have bounded waits. If setup/closure is unknown, the update media guard is retained; close owned setup windows and quit/reopen Millitop before retrying. Partial extraction/cache directories may be retained for diagnosis. An incomplete or invalid existing runtime is not silently overwritten. The runtime is app-owned local data and is not automatically deleted by removing a web tile.

## Pilot
Use only a test device first. Test a PC without Firefox, two different household profiles, declined setup, offline download, extension readiness, first site login and second launch, and unrelated personal Firefox running at the same time. Confirm both exact requested add-ons appear in the owned Firefox about:addons, the requested app opens after setup, the browser returns to Millitop on close, and updater/profile/Files/DVR/Gallery behavior remains intact. Payment-purpose isolation must be tested separately when the billing stage is supplied.

No Flutter, Windows, Mozilla extraction or extension installation was executed by the assistant. Structural checks and local source generation are not native-runtime certification; the installer must pass analysis/tests and the release's real-device pilot.
